## Part A — host avatar disappears when another member joins

### Findings against requested items 1–4

1. **One renderer/model shared by all members: ruled out in the inspected Creator and overlay paths.**
   - Creator stores renderers in `roomPreviewRenderers`, keyed by `member.user_id`, and constructs a new `AvatarRenderer` for each new member.
   - Overlay stores renderers in `playerRenderers`, also keyed by `member.user_id`.
   - Both paths render only `members.slice(0, 4)`; the Creator's source list is `roomMembers` loaded from the DB. This is not a single shared renderer, although the render-list cap and unsorted query remain problematic.

2. **Join RPC overwriting/deactivating host: not supported by inspected SQL.**
   - `vio_room_members` has primary key `(room_id,user_id)`; no slot/seat/order column exists in migration 001.
   - `vio_join_room` locks the room row, counts current members, and inserts a new row `(room_id,p_user_id,false)`. It does not update/delete the host row.
   - The RPC does not assign a stable seat. Room member queries do not explicitly order rows, so arrival/order can vary between snapshots.
   - Runtime DB rows before/after join were not queried; conclusion is source-level only.

3. **Per-participant background compositing: confirmed behavior and a strong direct cause when a participant has an opaque background.**
   - Every Creator participant gets a full-stage canvas and a separate `AvatarRenderer`.
   - `AvatarRenderer.render()` calls `drawBackground()` on every participant canvas before drawing that participant's sprite.
   - Creator composites those full canvases in sequence with `ctx.drawImage(entry.canvas,...)`. Overlay does the same.
   - If a later participant's profile background is solid, gradient, image, or video, that full-frame background is painted over all earlier participant sprites. This exactly explains the "only most recently drawn participant" symptom for affected profile backgrounds. If all backgrounds are transparent, this specific masking mechanism is inactive; actual profile background modes still need device/runtime confirmation.
   - Required architecture is one room background composited once, with member renderers drawing only member sprite/accessories/effects.

4. **Default layout instability: confirmed.**
   - `resolveRoomAvatarPreferences()` computes default X from `memberIndex` and `memberCount`: `(index - (count - 1)/2) * 34`.
   - Creator and overlay both pass current array index/count. Adding/removing/reordering members can change another member's default transform.
   - Creator's local participant additionally merges the local `roomOverrides` defaults, which initialize X/Y to zero, while remote members may receive index-derived defaults. This can make local and remote views resolve different layouts.
   - Explicit per-member X/Y overrides are not currently protected by a persistent slot assignment. A stable DB-backed slot is needed; do not key slots by array index.

### Additional render-list risk

- Both render paths slice the first four members.
- The Creator `room_members` query and overlay snapshot query do not specify `order()`.
- Renderer identity is member ID, but deterministic selection and layout still depend on an unspecified array order.
- Creator presence sync calls `loadRoomMembers()`; the stage's authoritative data is DB membership, not presence-only. Overlay's initial list comes from the DB snapshot. Keep this model and reconcile by member ID.

## Part B — one shared OBS link per room

### Confirmed unsafe behavior

- UI `index.html` exposes `Generate OBS Link` in the Collaboration room toolbar.
- Creator `generateOverlayLink()` calls `issue_room_overlay` on each initial generation.
- Edge Function `issue_room_overlay` generates a fresh random token, deletes every `vio_overlay_devices` row for the room, replaces `vio_rooms.overlay_token_hash`, and returns the new plaintext token.
- Therefore every generation can invalidate the previous URL. This is incompatible with a stable shared link.

### Existing schema limitation that must be resolved before safely implementing get-or-create

- Migration 001 stores only `overlay_token_hash` on `vio_rooms`; the raw token is not recoverable.
- `vio_overlay_devices` has `auth_user_id` as its primary key and `room_id` as a non-unique foreign key. It is used to authorize each overlay browser's own anonymous Auth session for Realtime.
- A unique index on `vio_overlay_devices.room_id` would break the current multi-browser authorization model because each overlay browser needs its own `auth_user_id` row.
- For already-active rooms, the server cannot return the existing plaintext URL from the current hash-only schema. Rotating to a new token would invalidate the old URL, contrary to the requirement not to break existing links.
- Recommended design for new rooms: a separate one-row-per-room canonical overlay-link record, with a stable token derivation or securely encrypted recoverable token, while retaining `vio_overlay_devices` as per-browser Realtime authorization sessions. The room-member-only get-or-create endpoint must return the same canonical URL to every member. Legacy active rooms require an explicit compatibility/migration policy; do not silently rotate their token.
- Never log or place the raw token in docs, tests, commits, or chat.

### Link UI

- Remove the Collaboration toolbar's `Generate OBS Link` control and replace it with `Salin link` and `Preview link` for all members.
- Both controls must fetch the same canonical server-issued URL; Preview must not issue or register another overlay device.
- The Solo editor's separate OBS generator is out of scope and should remain unchanged unless specifically requested.
